01

What this lab is about

Digital forensics is careful work with digital evidence: preserve the original, record what you do, and distinguish an observation from a conclusion.

01 /

Preserve first

I began with a supplied image file, recorded its hash and size, then worked from it in FTK Imager. A matching hash before and after is evidence that the file’s bytes did not change during this exercise.

02 /

Raw vs E01

A raw image is a direct byte-for-byte copy. E01 is a forensic container that can compress the image and store metadata and verification values. Their file hashes differ, even when E01 verifies the same underlying image data.

03 /

What a hash says

SHA-256 produces a digest that helps detect whether bytes differ from a recorded value. It does not show who handled a file, prove where it came from, or establish that a statement in it is true.

04 /

Deleted, not necessarily gone

In FAT, a deleted directory entry is marked with byte E5 at the start of its name. Here, the entry still points to a 161-byte synthetic note that was exportable. A deleted marker alone says nothing about who deleted it.

05 /

Slack & unallocated

File slack is the unused tail of the storage cluster assigned to a file; unallocated space is storage not currently assigned to a live file. The image exposes both as areas to examine, but this lab does not claim hidden real-world content from them.

SCOPE /

A constructed exercise

This is a synthetic teaching image with authored notes and timestamps. No physical USB device, real user, or real suspect is involved.

02

What I did

The seven steps follow the method documented in my lab report.

  1. 01

    Set a baseline

    Recorded the source image’s SHA-256 and byte length before opening it.

    SOURCE
  2. 02

    Inspect the image

    Loaded it as an image file in FTK Imager and reviewed the FAT16 tree, directory entries, and BUDGET.CSV.

    FAT16
  3. 03

    Create a raw image

    Made a full dd copy with verification enabled and independently compared its SHA-256 with the source.

    DD
  4. 04

    Create an E01 image

    Created a full E01 copy with verification enabled, then hashed the E01 container file.

    E01
  5. 05

    Verify again

    Reopened E01, confirmed the BUDGET.CSV preview, and ran Verify Drive/Image.

    VERIFY
  6. 06

    Export selected files

    Exported three live files and the deleted entry, then checked lengths and SHA-256 against fixture references.

    EXPORT
  7. 07

    Record and recheck

    Saved the directory listing, acquisition logs, and output hash manifest; re-hashed the source at the end.

    RECORD

What the evidence says

SUPPORTED BY THIS IMAGE

Observed

  • The source hash was unchanged across the exercise.
  • The raw and E01 images were verified; the raw SHA-256 equals the source.
  • All four exports matched the listed reference lengths and hashes.
  • The deleted entry retains 161 bytes of text mentioning BUDGET.CSV and a USB device.

BEYOND THIS EXERCISE

Not established

  • That any file was actually transferred.
  • Who wrote the note or used a device.
  • That authored names, times, or messages describe real events.
  • Any facts about a real person, suspect, or physical USB.

! A recovered statement is an observation about synthetic image contents, not proof of the event it describes.
